一、访谈与补充沟通

项目名称：酒店预订系统
甲方：韦依彤；需求分析工程师：徐一帆

正式访谈 INT-01（时间：2026/10/24）
INT-01-L001 系统有几种不同的用户类型？每种用户都有什么操作权限？
INT-01-L002 甲方：系统设三类用户，顾客、酒店工作人员和平台管理员。权限边界上，顾客只能操作自己的预订；酒店工作人员只能操作本酒店数据；平台管理员偏管理和审计。

INT-01-L003 乙方：这个系统需要支持面向普通用户的哪几类业务？
INT-01-L004 甲方：面向普通用户的业务，主要有这几类：
1. 查询酒店和房型：按城市、日期、人数、房型、价格查。
2. 预订：选房型、日期、人数，发起预订。
3. 查看和管理自己的预订：查看预订详情，修改或取消。
4. 入住和退房：配合酒店办理入住、退房。
5. 了解无房和停售情况：查询时能看到无房、临时停业等状态，避免无效预订。

INT-01-L005 乙方：这个系统需要支持面向酒店工作人员的哪几类业务？
INT-01-L006 甲方：面向酒店工作人员，主要有这几类：
1. 酒店和房型管理：维护本酒店信息、房型信息。
2. 每日库存管理：设置和维护各房型每日可售库存。
3. 价格管理：设置和维护每日价格。
4. 停售管理：设置临时停业、房型停售等状态。
5. 预订处理：查看本酒店预订，确认预订，处理顾客的修改和取消。
6. 入住退房办理：为顾客办理入住、退房，更新房间状态。
7. 异常处理：处理无房、临时停业等情况。
权限上只限本酒店数据，不跨酒店操作。

INT-01-L007 乙方：需要支持面向系统管理员的哪几类业务？
INT-01-L008 甲方：面向平台管理员，主要有以下几类业务：
1. 酒店和账号管理：维护酒店基础信息，管理顾客、酒店工作人员等账号。
2. 权限管理：分配和调整各类用户权限。
3. 全局查询与监督：查看全局酒店、房型、库存、价格和预订情况。
4. 异常处理：处理无房、临时停业、预订异常等问题。
5. 操作记录审计：查看关键操作记录，用于追溯和核对。
权限上偏管理和审计，不直接替酒店做日常房态操作，除非管理需要。

INT-01-L009 乙方：这个系统要记录哪几类数据？这些数据之间有什么关系？
INT-01-L010 甲方：系统主要记录以下几类数据：
1. 用户数据：顾客、酒店工作人员、平台管理员，含角色和权限。
2. 酒店数据：酒店基本信息，归属关系。
3. 房型数据：房型信息，属于某家酒店。
4. 每日库存数据：某房型某日期的可售库存、价格、停售状态。
5. 预订数据：顾客、酒店、房型、入住日期、离店日期、人数、金额、状态。
6. 房间状态数据：房间的可用、已预订、已入住、退房、停售等状态。
7. 操作记录数据：关键操作的时间、操作人、操作对象和结果。
数据关系：
1. 用户通过角色和权限关联到可执行的操作。
2. 酒店包含多个房型。
3. 房型按日期对应每日库存、价格和停售信息。
4. 预订关联顾客、酒店、房型和具体日期，并占用对应日期的库存。
5. 房间状态与预订和入住退房关联。
6. 操作记录关联操作人、操作对象和对应业务数据，用于追溯。

INT-01-L011 乙方：哪些数据是不能重复出现的？比如同一个房间应该只能有一条有效预约。
INT-01-L012 甲方：以下数据需要保证不重复或唯一：
1. 用户账号：同一登录名只能对应一个有效账号。
2. 酒店与房型的标识：酒店、房型应有唯一标识，避免重复建档。
3. 每日库存记录：同一房型、同一日期只能有一条有效库存记录，不能出现两条互相冲突的库存。
4. 价格和停售记录：同一房型、同一日期应只有一条生效的价格和停售状态，避免同一日期多个价格并存。
5. 房间的有效占用：同一个具体房间在同一日期区间内只能有一条有效预约/入住占用，不能重叠。
6. 同一顾客对同一房型、同一日期区间不应产生重复的有效预订。
其中你举的例子成立，同一个房间在同一有效日期区间内只能有一条有效预约。

INT-01-L013 乙方：哪些数据需要同步更新？
INT-01-L014 甲方：以下数据之间需要同步更新：
1. 预订与每日库存：预订成功要扣减对应房型每日库存；取消、修改、退房要按规则回滚或调整库存。
2. 预订与房间状态：预订占用房间，入住、退房、取消要同步更新房间状态，避免同一房间重复占用。
3. 预订与价格：下单时保存当时价格；改价只影响后续预订，不改已确认预订的价格。
4. 房型与每日库存、价格、停售：房型新增、停用或停售时，要同步对应日期的库存和价格设置。
5. 临时停业与库存、预订：停业要同步停售对应日期库存，并处理或拒绝受影响的预订。
6. 入住退房与库存、房间状态：入住和退房要同步房间状态，退房后按规则恢复可售或进入清洁状态。
7. 关键操作与操作记录：预订、确认、修改、取消、入住、退房、停售等操作要同步写操作记录。
8. 用户权限与业务操作：权限变更后，相关操作入口和校验要同步生效。

INT-01-L015 乙方：这个系统主要需要实现怎样的多条件查询？
INT-01-L016 甲方：系统主要需要实现以下几类多条件查询：
1. 按城市查询。
2. 按日期查库存：查某酒店或某房型在指定日期区间的每日库存和可售状态。
3. 按价格查：按价格区间筛选房型，区分当前价格和预订时保存的价格。
4. 按房型查：按房型名称、床型、容纳人数等条件筛选。

INT-01-L017 乙方：需要实现怎样的统计功能？
INT-01-L018 甲方：按酒店和日期区间统计预订与入住情况，统计预订数、确认数、取消数、入住数、退房数，按房型和日期分组，算取消率和入住率，金额以下单时保存的价格为准。

INT-01-L019 乙方： 需要实现怎样的异常处理？
INT-01-L020 甲方：系统需要实现以下异常处理：
1. 无房处理：预订时无可用库存要能识别并拒绝，给出明确提示。
2. 临时停业处理：停业期间拒绝新预订，并处理已受影响的预订。
3. 最后一间房争抢处理：多人同时预订时，只能一人成功，其余人得到无房结果。
4. 修改和取消异常处理：状态不允许修改或取消时要拒绝。
5. 房间状态冲突处理：入住退房状态不合法时要拒绝。
6. 越权和非法操作处理：权限不足或非法状态迁移要拒绝。

INT-01-L021 乙方：有哪些非功能性需求，以及通过标准是什么?
INT-01-L022 甲方：非功能性需求：
1. 性能：多人同时预订最后一间房时不能超卖，查询响应要可接受。
2. 一致性：库存、预订、房间状态、价格、停售数据在状态变更后保持一致。
3. 可靠性：重复提交、异常操作不能产生脏数据，失败要能回滚。
4. 安全性：三类用户权限隔离，顾客不能操作他人预订，酒店不能跨店操作。
5. 易用性：查询条件清楚，无房、停售、状态不允许等提示明确。
通过标准：
1. 功能覆盖：三类角色权限、酒店房型管理、每日库存价格停售、多条件查询、预订确认修改取消入住退房都能跑通。
2. 关键场景正确：最后一间房不超卖，重复预订不重复占库存，跨日库存正确扣减和回滚。
3. 异常处理到位：无房、临时停业、状态冲突、越权操作都能正确拒绝或处理。
4. 数据一致：库存、预订、房间状态、价格、停售和操作记录同步一致。
5. 演示完整：能完整演示查询、预订、确认、入住、退房、取消、异常处理全流程。


跟进沟通 INT-02（时间：2026/10/25）
INT-02-L001 乙方：这个系统的登录、注册机制是怎样的？
INT-02-L002 甲方：顾客采用自助注册和登录，使用手机号或账号加密码完成注册与登录。酒店工作人员和平台管理员不开放自助注册，由平台管理员在后台创建账号并分配角色及所属酒店，账号创建后由本人登录使用。登录时进行账号密码校验，登录成功后系统依据角色控制可见数据和可执行操作，酒店工作人员仅能访问本酒店数据，平台管理员可查看全局信息，但日常房态操作仍由酒店工作人员执行。

INT-02-L003 乙方：系统有支付环节吗，支付环节和预订的关系是什么？
INT-02-L004 甲方： 有支付环节，但本项目只做模拟支付，不接真实支付网关。支付环节是预订流程中的一段状态，不是独立于预订之外的另一个系统。

关系上是这样：顾客发起预订后，预订先进入待支付状态，这时库存要预占住，不能让别人订走；顾客完成模拟支付后，预订变为已支付，酒店工作人员才能确认预订。如果顾客一直不支付，预订可以超时取消并释放库存；顾客取消或酒店无法履约时，走模拟退款，只改预订状态和写操作记录，不涉及真实资金流转。所以支付是预订状态机里的一环，预订是主体，支付是推动预订从待支付走到已支付的动作。

INT-02-L005 乙方：预订状态的流转规则是什么？
INT-02-L006 甲方：预订状态大体这样流转：顾客提交预订后进入待支付，这时库存预占住。模拟支付完成后变成已支付，酒店工作人员确认后变成已确认。到了入住日，酒店办理入住变成已入住，退房后变成已退房，流程结束。

中间有几个分支：待支付阶段顾客可以主动取消，或者超时未支付系统自动取消，取消后释放库存；已支付但酒店还没确认时，顾客可以取消，走模拟退款；已确认之后要取消，需要酒店同意或按规则处理，同样释放库存并模拟退款。酒店这边如果无房或临时停业无法履约，可以拒绝或取消预订，也要释放库存并走退款。

状态迁移必须合法，比如已退房的不能再取消，已取消的不能再入住，非法迁移直接拒绝并记录。这样预订、库存、支付状态就能保持一致。

INT-02-L007 乙方：退房后房间是立刻转为可售，还是变成清洁中之类的？
INT-02-L008 甲方：退房后直接转为可售，不再单独设清洁中状态。

INT-02-L009 乙方：停售恢复后，库存如何恢复？
INT-02-L010 甲方：停售只是把房型或日期标记为不可售，库存数字本身不会被清掉。恢复停售就是取消停售标记，原来剩多少库存还是多少，不额外增加也不重置。停售期间已经取消的预订按规则回滚的库存也照常保留，恢复后一起可售。

INT-02-L011 乙方：如果酒店停业，受到影响的预订如何处理？
INT-02-L012 甲方：停业时，受影响的预订不自动取消，先由酒店工作人员联系顾客处理。系统只把停业日期标记为不可售，拒绝新预订；已经存在的预订保持原状态，但标记为待处理。然后酒店可以选择为顾客改期到其他日期，或者取消并模拟退款。

INT-02-L013 乙方： 查询响应性能的测试环境和数据规模具体如何？
INT-02-L014 甲方： 测试环境按单机部署，应用和数据库跑在同一台普通服务器上，配置 4 核 8G 即可，压测工具单独在另一台机器或本机发起。数据规模按中小型平台准备：酒店表约一千条，房型表约几千条，每日库存表按房型乘未来三十天生成，约三万条记录，预订表准备几千到一万条。并发按 20 到 50 个并发查询用户验证。通过标准是在该环境下，90% 以上的查询请求在 1 秒内返回，不出现超时或错误。重点验证查询逻辑和索引设计在合理并发下的表现，不追求大型平台的海量数据场景。

INT-02-L015 乙方： 怎么算查询超时和失败？超时和失败如何处理？
INT-02-L016 甲方： 查询接口定 3 秒为超时上限，超过 3 秒未返回就算超时。请求返回错误状态码、返回内容不完整或数据库报错，就算失败。

INT-02-L017 乙方： "管理需要"触发管理员直接操作的具体情形和审批方式是什么？
INT-02-L018 甲方： 酒店失联或违规导致预订异常时，管理员可以强制取消预订。需要填写原因，系统记下操作人和时间。

INT-02-L019 乙方： 管理员处理和酒店工作人员处理的冲突如何仲裁？
INT-02-L020 甲方： 酒店工作人员负责日常操作，管理员只在酒店失联或违规时强制介入，管理员操作以管理员结果为准。两边同时改同一条数据时，先成功的生效，后操作的提示刷新重试，管理员操作留原因和记录。

INT-02-L021 乙方： 什么叫做“管理员操作以管理员结果为准”？
INT-02-L022 甲方： 这句话的意思是，当管理员执行强制操作时，比如强制取消一笔预订，系统不会再问酒店同不同意，也不会被酒店的日常操作挡回去，最终以管理员的操作为最终结果。

INT-02-L023 乙方：统计功能的使用范围是怎样的？
INT-02-L024 甲方：统计功能主要给酒店工作人员和平台管理员用。酒店工作人员只能看本酒店按日期区间的预订与入住统计，包括预订数、确认数、取消数、入住数、退房数，按房型和日期分组，算取消率和入住率，金额以下单时保存的价格为准。平台管理员可以看全局或指定酒店的同类统计。

处理上，超时由前端或网关中断请求并提示用户“查询超时，请稍后重试”，不返回半截数据；失败则记录错误日志和操作记录，向用户返回明确的失败提示，不把数据库错误直接暴露给用户。超时和失败都不修改任何业务数据，用户可重试。压测时统计超时率和失败率，作为查询性能验收的一部分。

INT-02-L025 乙方：越权提示怎么实现？这个系统是要对不同角色开放不同的前端吗？
INT-02-L026 甲方：越权提示分两层做。前端按角色开放不同页面和菜单，顾客看不到酒店后台和管理员页面，酒店工作人员看不到其他酒店和管理员功能，管理员有管理页面。这只是界面层，不能当安全边界。

真正的越权拦截在后端：每个接口都校验当前登录用户角色和数归属，顾客只能查改自己的预订，酒店工作人员只能操作本酒店数据，管理员按管理权限校验。校验不通过就返回明确的越权提示，比如“无权操作该预订”或“无权访问该酒店数据”，同时记操作记录。前端再根据返回提示用户，不暴露具体数据。

所以不同角色前端入口不同，但权限控制以后端校验为准，前端只负责展示和引导。

INT-02-L027 乙方：权限变更或者账号被停用对当前会话的生效时机是怎样的？
INT-02-L028 甲方：权限变更或账号停用后，不保证立刻踢掉已经登录的会话。简单做法是：每次请求后端都重新校验当前账号状态和权限，账号停用或权限变更后，旧会话再发请求就会被拒绝或按新权限处理。

INT-02-L029 乙方：如果前一单离店日期和后一单的入住日期是同一天，怎么处理？
INT-02-L030 甲方：按酒店惯例，离店日当天房间可以给下一位客人入住，所以前一单离店日期和后一单入住日期是同一天，不算冲突，是允许的。库存占用按“入住日到离店日前一天”逐日计算，离店日不占库存，这样两单首尾相接正好衔接。

INT-02-L031 乙方：同一房型同一日期如果被重复设置了库存，应该更新原来的记录还是拒绝？也就是并发如何处理？
INT-02-L032 甲方：同一房型同一日期本来就只允许一条库存记录，所以重复设置统一按“更新原记录”处理，不新增第二条。
并发上，两个工作人员同时改同一条库存记录时，用版本号或条件更新来防覆盖：读的时候带出版本号，提交时校验版本号，没变就更新并让版本号加一；变了就拒绝这次更新，提示“数据已被他人修改，请刷新后重试”。这样不会静默覆盖，也不用手动加锁。

INT-02-L033 乙方：多个工作人员修改同一条记录如何处理？
INT-02-L034 甲方：多个工作人员修改同一条记录时，用版本号或条件更新来处理。每个人读取记录时拿到当前版本号，提交修改时带上这个版本号，系统只允许版本号一致的那次更新成功，并把版本号加一。后提交的人版本号已经对不上，更新会失败，系统提示“数据已被他人修改，请刷新后重试”，不会静默覆盖前一个人的修改。课程项目里这样就够了，不需要额外的锁机制或人工仲裁。
